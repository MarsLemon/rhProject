# wk-user 学习中心账号同步 1.5 改动说明

> 面向：接手同步功能的开发/运维。只讲 wk-user 侧（发送方），不含 train-center。
> 日期：2026-07-28

---

## 一、这次解决了什么问题

学习中心（train-center）里 790 个用户大量缺工号 / 职务 / 部门。根因在 wk-user 推送这一侧，1.5 做了四件事：

1. **补齐字段**：工号 / 姓名 / 手机无条件推、部门职务尽量推。
2. **增量同步**：不再每天全量直推，只推「今天动过的人」，量小可控。
3. **离职 / 停用冻结**：离职员工、停用账号推「禁用」状态，学习中心随之冻结。
4. **企业用户不同步**：merchant（供应商成员）不该进学习中心，全量 + 增量都排除。

外加两项工程质量改造：**按 DDD 把同步逻辑抽成独立应用服务**、**消除批量同步的 N+1 查询**。

---

## 二、同步是怎么跑的

```
xxl-job「trainCenterUserSyncTask」
   │  参数：空/不填 → 增量(近25h)   full → 全量兜底   数字N → 增量(近Nh，手动补跑)
   ▼
TrainCenterUserSyncAppService（应用服务，编排用例）
   ├─ syncChanged(hours)：查四表 update_time 变更的人 → 只推这批
   ├─ syncAll()：推全部（仅在职员工）
   │     └─ 组装时：批量取部门/职务 + 员工信息（一次性，不在循环里查）
   │        · 企业用户 merchant → 跳过
   │        · 离职员工 → 带 state=禁用
   │        · 追加「已停用账号」的冻结指令
   ▼
TrainCenterUserSyncService（领域网关）→ RestTemplate HTTP 推到 train-center
```

**关联键**：train 侧 `el_sys_user.id` = wk-user 的 `user_code`（UC 开头）。

**触发时机**：
- 每天定时增量（推荐 3 点，参数留空）。
- 每周全量兜底一次（参数 `full`，纠偏）。
- 加「学习中心角色」时实时单人同步（`RoleServiceImpl.batchAddRoleUser` 异步容错 / `UserServiceImpl.addUserRole` 事务内——见第七章遗留风险）。

## 三、关键规则（容易踩的点）

| 规则 | 说明 |
|---|---|
| 只同步公司员工 | `userType == merchant` 直接跳过；`userType` 为空的历史数据仍按基础信息推（保持旧行为） |
| 离职冻结 | 员工 `employee_state=0` → 推 `state=禁用`，train 侧冻结账号 |
| 停用账号冻结 | `wk_user.state≠1` 的账号（不在 allUser 内）单独追加冻结指令；**含已停用 merchant**（有意为之，用来清理 train 侧历史残留 merchant 账号，未同步过的则无副作用） |
| 只冻不解 | 只推禁用、不主动解冻，避免覆盖管理端手动禁用 |
| 增量窗口 25h | 24h + 1h 重叠，防调度抖动漏数据 |
| 单人容错 | 组装单个用户失败只跳过该人，不中断整批 |

## 四、改了哪些文件

### 提交 1：`28a06b0b` 增量同步 + 状态禁用
- 新增增量能力：`UserMapper.xml` / `UserDao` / `UserRepository(+Impl)` 的 `findChangedUserCodes`（四表 update_time UNION）、`listDisabledUserCodes`。
- 新增定时任务：`TrainCenterUserSyncTask`（参数分流：空/full/数字）。
- 协议加 `state` 字段透传（**仅批量同步链路** `TrainCenterUserSyncInfoCommand`）：`TrainCenterUserSyncInfoCommand` / `TrainCenterUserSyncInfo` / `TrainCenterUserSyncServiceImpl` / `TrainCenterConstants`。单条加角色链路 `TrainCenterUserSyncCommand` 不含 `state`（加角色时用户必为启用态，无需）。
- 发送端加固：`TrainCenterUserSyncRepositoryImpl`（HTTP 超时 + 成功码校验 + state）。
- 任职查询过滤：`EmployeeDepartmentMapper.xml`（在职 + 任职期内 + 排除兼职）。

### 提交 2：`a0bac1f2` DDD 抽取
- 新增应用服务 `TrainCenterUserSyncAppService(+Impl)`：承接 `querySyncInfo` / `syncAll` / `syncChanged` 三个用例 + 组装/冻结私有逻辑。
- `UserService` / `UserServiceImpl` **卸掉批量同步方法**（`userSyncInfo`/`userSyncAllInfo`/`userSyncChangedInfo`/`syncUsersToTrainCenter`），回归用户自身职责。注意：加角色触发的**单条同步** `addUserRole` 仍走老入口（未动，见第七章）。
- `WkUserController`、`TrainCenterUserSyncTask` 改调新应用服务（**HTTP 接口路径/入参/返回不变**）。
- `UserSyncInfoBo` 迁到 `service.traincenter.model`（消除反向依赖）。

### 未提交：N+1 消除（批量查询抽独立类）
问题：全量组装时循环内每人查 1 次 DB + 2 次 Feign（部门/职务），790 人 ≈ 800 DB + 1600 Feign。
改法：**批量预取 + 内存组装**，且抽成同步自有的独立类，不动他人文件：
- 新增 `service/traincenter/dao/EmployeeDeptSyncDao` + `model/EmployeeDeptSyncRow` + `mapper/TrainCenterEmployeeDeptSyncMapper.xml`（一次 IN 取有效任职）。
- 新增 `service/traincenter/EmployeeDeptSyncBatchQuery(+Impl)`：1 次批 DB + 各 1 次批 Feign（`getChildDepartmentListByIdList` / `getFunctionListByIdList`）→ 组装 `Map<员工编号, 部门职务信息>`。
- `TrainCenterUserSyncAppServiceImpl` 改注入它；循环内纯内存组装。
- 复杂度：~1600 次调用 → 4 次批量。

## 八、设计原则（本次确立，后续沿用）

1. 能单独抽离的类就单独抽离——新功能落在自有新类/新包/新 Mapper。
2. 尽量不动他人既有代码——除非评判确需改源文件（如同步接收端本身必须改）。
3. 只改自己新建的文件可自由，动他人文件先评判。
