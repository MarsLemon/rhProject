## 二、四审关键发现（3 项 P0）

### P0-#1：mobile 端已有 `axios-retry@^4.4.1`，但 SSE 重连方案要拍板

**开工建议声称**（§四 调整表）：
> mobile 自带 SSE 重连（不等 v3），包一层 `aiGatewaySse.ts`

**仓库事实**：
- `wk-mhc-mobile/package.json:30` 已装 `axios-retry@^4.4.1`
- `src/utils/http.ts` 是 axios 封装，**但 grep retry/重连/reconnect 关键词无命中**——axios-retry 已装但**未启用**
- SSE 长连接走 `fetch + ReadableStream`（不走 axios），**axios-retry 帮不上 SSE 的忙**

**问题**：
- 如果主人拍板"mobile 自带重连"，执行者需要**自己实现指数退避**
- 但仓库已有 axios-retry 依赖，**为什么不用**？是因为历史原因没用，还是有更深的考量？
- 重连算法要不要复用 axios-retry 的指数退避逻辑（写到 SSE 层用）？

**建议补**：Phase 1.1 拆为：
- 1.1a：调研 axios-retry 在项目里为什么没用 + 是否可参考其退避算法移植到 SSE 层
- 1.1b：实现 aiGatewaySse.ts 的重连（参照 axios-retry 的指数退避 + jitter 算法）
- 1.1c：单测覆盖断线场景（mock fetch 抛 AbortError）

**决策点**：Phase 0.8 新增——"mobile SSE 重连实现方案 + 是否复用 axios-retry 退避算法"

### P0-#3：useChatSession.ts 拆分边界未给具体方案

**开工建议声称**（§三 Phase 0.7）：
> 评估 useChatSession.ts 765 行是否需拆

**问题**：
- "是否需拆"是个开放问题，**没有拆分候选方案**
- 执行者 Phase 0.7 调研时会卡——不知道该往哪些边界拆

**仓库事实**（基于之前读到的 useChatSession.ts 用法推断 + 实际看 pages/smart-training/components/ai/ 的引用关系）：
- useChatSession.ts 765 行大概率涵盖：消息列表状态 / SSE 收发 / 历史分页 / 中断恢复 / 模式切换 / 文件附件管理
- 调用方 10 个，全部是 `pages/smart-training/components/ai/*.vue`
- **没有跨业务模块调用**（im/inbox/order 不依赖）

**建议补**：开工建议 §三 Phase 0.7 给出**默认拆分方案**作为基线：

```
方案 A（保守）：保留 765 行，Phase 2 仅扩展方法
  风险：突破 1000 行后维护困难
  工期：0 额外

方案 B（推荐）：拆为 3 个 composable
  - useChatCore.ts（消息列表 + 收发状态，约 350 行）
  - useChatHistory.ts（历史分页 + 上下文加载，约 250 行）
  - useChatInterrupt.ts（中断恢复 + 重试，约 165 行）
  风险：调用方需要小幅调整
  工期：+0.5 天

方案 C（激进）：拆为 5 个 composable（按职责更细分）
  风险：过度拆分
  工期：+1.5 天
```

**决策点**：默认走方案 B，Phase 0.7 仅做最后拍板。

## 三、其他执行盲点（P1-P2）

### P1：路由系统类型来源未确认

`typed-router.d.ts` 第 24 行有 `/ai/history` 路由定义（grep 命中）。这意味着 mobile 端用了 unplugin-vue-router 这种自动生成路由类型的方案。

**问题**：
- 删除 `/ai/index` 和 `/ai/history` 路由时，`typed-router.d.ts` 是否会自动重生成？
- 还是需要手动维护？

**建议补**：Phase 6.4 增加：
- 验证 unplugin-vue-router 是否自动重生 typed-router.d.ts
- 如不自动，手动删除该 RouteRecordInfo

### P1：mobile 后端 SSE 真实 URL 路径未确认

开工建议 §二 行动 2 的 issue 文本提到 `/api/wk/ai/agent/chat-stream`，**但这是计划推测的路径**，实际可能不同。

**仓库事实**：
- 后端 `WkAiAgentController.java` 存在（grep 命中）
- 路径前缀可能是 `/aiGateway/chatStream`（计划 §1.3 早期版本）或 `/api/wk/ai/agent/chat-stream`（修正版）
- **两次列的路径不一样！**

**建议补**：Phase 0.3 POC 验证时第一件事就是**确认后端 SSE 真实 URL**。如果路径错了，整个 Phase 2.1 都要改。

### P1：Phase 7 增量（埋点/灰度/回滚）缺主语

开工建议 §四 Phase 7 增量列了 7.8-7.11，但**没说谁来负责**：
- 埋点对接 → 前端 owner 还是数据 owner？
- 监控指标 → 运维 owner？
- 灰度方案 → 客户端发版 owner？

**建议补**：Phase 7 增量每项标注 owner 角色（如"前端 owner 提交 + 数据 owner 评审"）。

### P2：mobile 现有 useChatSession.ts 是不是已经在用后端真实 SSE？

开工建议 §三 Phase 0.3 写"验证 mobile useChatSession.ts 对接后端 AI 网关 SSE 的可行性"——但**这暗示 mobile 端目前还没对接真实后端**。

**仓库事实**：
- mobile 已有 `pages/ai/index.vue` + `pages/ai/history.vue`（旧入口）
- mobile 已有完整的 `useChatSession.ts` 765 行 + `AnswerAssistantView.vue` / `TrainingAssistantView.vue`
- 这些**必然已经在跑某个 SSE 后端**（否则现有功能无法工作）

**问题**：
- mobile 现有 SSE 后端是 `/aiGateway/chatStream`（计划旧版）还是 `/api/wk/ai/agent/chat-stream`（新版）？
- 现有后端协议是 13 种 type 路由还是简化的 data:/[DONE]？

**建议补**：Phase 0.0 新增（最先做）——**"摸清 mobile 现有 AI 后端契约"**：
- 读 mobile `adapters.ts` 看 API 路径
- 读 mobile `useChatSession.ts` 看 SSE 解析逻辑
- 读后端 `AgentReActExecutorImpl.java` 看发包格式
- 产出：mobile 现有 SSE 后端契约文档

**这一步比 Phase 0.1 还优先**——如果 mobile 已经在用某个后端，Phase 1 起的所有"对接网关"都是迁移，不是从零对接。
