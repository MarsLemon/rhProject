### P0-#2：v3 sseStream.ts 协议兼容性（13 种 type 路由支持）

**二审结论**：v3 只处理 data:/[DONE]，不能直接复用，需扩展为 type 路由。
**三审复核**——**读完 v3 sseStream.ts 全文 271 行后**：

实际能力（第 187-232 行）：
```typescript
// 第 187 行：[DONE] 结束标记
if (dataStr === '[DONE]') { ... return }

// 第 197-210 行：JSON 解析失败时降级为纯文本
let obj: any = null
try {
  obj = JSON.parse(dataStr)
} catch {
  // 非 JSON 字符串,作为纯文本追加
  fullText += dataStr
  ...
}

// 第 212-232 行：成功解析 JSON 后,提取字段
const delta =
  typeof obj.delta === 'string' ? obj.delta
  : typeof obj.text === 'string' ? obj.text
  : typeof obj.content === 'string' ? obj.content
  : ''

lastChunk = {
  fullText, delta,
  sessionId: obj.sessionId || obj.session_id || ...,
  requestId: obj.requestId || obj.request_id || ...,
  citations: obj.citations || ...,
  thoughts: obj.thoughts || ...,
  fileList: obj.fileList || obj.file_list || ...,
  raw: obj          // ← 关键:整个 chunk 对象透传
}
```

**三审结论**：
1. v3 sseStream.ts **确实做了 JSON 解析**，不是二审说的"只处理 data:/[DONE]"
2. v3 提取的字段是 `delta / text / content / sessionId / requestId / citations / thoughts / fileList` —— **不包含 `type` 字段**
3. 但 **`raw: obj` 把整个 chunk 对象透传给了 `onChunk` 回调**
4. 业务层 `onChunk` 拿到 `chunk.raw` 后，**自己按 `chunk.raw.type` 路由**就行（content / thoughts / tool_call / ...）

**所以**：v3 sseStream.ts **够用**，不需要扩展 type 路由机制。**业务层写 13 个 type 的 if-else 分发即可**。

**降级为非阻塞**：从 P0 降到 P1（实施注意项）。

**风险**：13 个 type 全部走 `if-else` 不优雅。但这是业务组织问题，不是工具问题。后续可重构为 type→handler Map。

**附：v3 sseStream.ts 的"占位 fallback"真相**

二审 §5.2 担心 v3 store 走"占位 fallback"。读完 sseStream.ts 全文发现：
- sseStream.ts 工具本身**没有 fallback 逻辑**——就是标准的 fetch + ReadableStream

实际需要验证的是 `stores/modules/ai.ts:fetchSseOrFallback` 的具体逻辑（mobile 端不直接用 v3 store，所以无关）。

### 4.2 v3 sseStream.ts 的 token 兼容性问题（二审未深入）

**三审发现**（读 sseStream.ts 第 121-130 行）：
```typescript
const fetchHeaders: Record<string, string> = {
  Accept: 'text/event-stream',
  ...headers
}
if (!fetchHeaders['token'] && !fetchHeaders['Authorization']) {
  const token = getToken()
  if (token) {
    fetchHeaders['token'] = token
  }
}
```

**关键**：v3 sseStream.ts 用 `getToken()` 从 `@/utils/auth/token` 取 token，注入到 `token` header（**不是标准 `Authorization: Bearer`**）。

**mobile 端 token 机制核对**：grep mobile 端 `getToken` 实现——
- 实际上手机端 token 通常由 axios request 拦截器统一注入
- v3 这套 `token` 自定义 header 在 mobile 后端可能不被认可

**Phase 0.4 调研项的关键问题**：
- mobile 后端识别的是 `Authorization: Bearer xxx` 还是自定义 `token` header？
- 如果是 Authorization，**mobile 端要改 sseStream.ts 的 header 名**
- 这是 Phase 0 必须明确的事，**不是 Phase 1.5 才改**

**建议**：Phase 0.4 优先级提升为 P0（开工前必查）。

### 4.3 mobile 端 `useChatSession.ts` 已有 765 行——是否需要拆？

**事实**：mobile 端 useChatSession.ts（765 行）已包含消息收发、历史分页、中断恢复。
**问题**：plan 把它当"扩展"目标，但没说怎么扩展——直接加方法会让它突破 1000 行。

**建议**：Phase 2.4 增加方法前，先**评估是否需要拆 useChatSession.ts**：
- 拆 A：`useChatSession.ts`（核心消息收发） + `useChatHistory.ts`（历史分页） + `useChatInterrupt.ts`（中断恢复）
- 拆 B：保留 765 行，新增方法到 900-1000 行（二审风险）

**决策项**：Phase 0 增加 0.7：评估 useChatSession.ts 拆分方案。

### 4.4 mobile 端 `pages/smart-training/utils/splitChatAttachments.ts` 也引用 composables/ai

### 4.6 mobile 端 markdown 渲染 vs v3 markdownRenderer.ts 的兼容性

**事实**：
- v3 `markdownRenderer.ts`（83 行）：marked@^14 + sanitizeHtml + 引用编号处理
- mobile 端 `composables/ai/useMarkdown.ts`（独立实现，配套 spec）：已有自己的 markdown 方案

**问题**：plan §2.2 把 v3 `markdownRenderer.ts` 列为"直接复制"，但 mobile 端已经有 `useMarkdown.ts` 在用。

**三审建议**：
- 不要替换 mobile 现有的 `useMarkdown.ts`（避免大改动 + 单测失效）
- 但 v3 `markdownRenderer.ts` 的引用编号处理 `[N] → <sup class="citation-ref">[N]</sup>` 和 ##(\d+)\$\$ 标记是 mobile 缺的 → **只复制 v3 的两个处理函数**，整合进 mobile 现有 useMarkdown

### 4.7 后端 SSE 13 种事件的 chunk 形态

**事实**（读 AgentChatChunkVo.java 头注释 + 字段定义）：
- 每个事件 type 字段区分

**mobile 端 useChatSession.ts 当前的 SSE 解析**（凭推断，未读全文）：大概率只解析 content/citations 几个字段。

**Phase 2.3 类型定义补充**：

- 要补每个 type 对应的 payload 字段类型
- 来源：`AgentChatChunkVo.java` 全部字段（含 List<Object> thoughts、Map metadata 等）
