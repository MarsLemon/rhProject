## 三、残留事实偏差（开工前必改）

### 偏差 #1：mobile `composables/ai/voice/` 文件数

**计划声称**：
> mobile `pages/smart-training/composables/ai/voice/`（9 文件）— `useVoiceRecorder` / `useVoiceAsr` / `useVoiceTts` / `mediaCapture` / `parseAsrPlainText` / `ttsPlainText` 等

**仓库事实**：
```
pages/smart-training/composables/ai/voice/
├── mediaCapture.ts
├── parseAsrPlainText.ts
├── parseAsrPlainText.spec.ts
├── tts-plain-text-contract.json
├── ttsPlainText.ts
├── ttsPlainText.spec.ts
├── useVoiceAsr.ts
├── useVoiceRecorder.ts
└── useVoiceTts.ts
```

实际 **9 个文件没错**，但计划 §1.2 表格分类列了 4 项（voiceRecorder / voiceAsr / voiceTts / mediaCapture + parseAsr + tts-plain-text 共 6 个），把"配置/单测/spec"也算入"语音能力"，**混淆了"能力"和"测试/契约"**。

**修复建议**：§1.2 表格改为分两组：
- 能力：`useVoiceRecorder` / `useVoiceAsr` / `useVoiceTts` / `mediaCapture` / `parseAsrPlainText` / `ttsPlainText`（6 个）
- 配套：`*.spec.ts`（3 个）+ `tts-plain-text-contract.json`（1 个）

**影响**：中等。Phase 4 的"语音集成"步骤实际只动能力文件，spec 不需要动。

### 偏差 #2：mobile `conversationRules.ts` 与 v2 同名模块的关系

**计划声称**：
> v3 缺失关键能力：`conversationRules.js`（74 行）+ `historyContext.js`（142 行）—— v3 缺失此逻辑，需从 v2 移植
>
> Phase 1.2：从 v2 TS 重写 2 个域逻辑（conversationRules, historyContext）→ `mobile/src/shared/ai/`

**仓库事实**：
- mobile 端**已经存在** `pages/smart-training/composables/ai/conversationRules.ts`（42 行）
- 内容是 `isWelcomeOnlyMessages` / `isEmptyRecordList` / `StartNewSessionResult` —— **与 v2 conversationRules.js 的职责完全不同**
  - v2 conversationRules.js（73 行）：**会话上下文窗口裁剪**（按 maxTokens / maxMessages 截断历史）
  - mobile conversationRules.ts（42 行）：**会话启动判定**（判断是否只剩欢迎语、是否空会话、是否可复用）
- **v2 historyContext.js（141 行）**：根据文件命名与一审 review 应是"历史消息上下文"封装（用于上下文窗口裁剪）
- mobile 端**没有 historyContext.ts**

**结论**：
1. plan §1.1 表中"v3 缺失上下文窗口裁剪"是对的（v3 ai.ts 确实可能没做）
2. **但 plan 把"mobile 已有 conversationRules.ts"和"v2 缺的 conversationRules.js"当成一回事**——这两个同名模块职责完全不同
3. 实际要做的是：**从 v2 `conversationRules.js`（73 行）补一个 `shared/ai/conversationContextRules.ts`（避免与 mobile 现有 `conversationRules.ts` 重名）**，用于上下文窗口裁剪
4. mobile 现有 `conversationRules.ts`（会话启动判定）保留

**修复建议**：Phase 1.2 改名：
- 旧：`shared/ai/conversationRules.ts`（与 mobile 现有重名 → 冲突）
- 新：`shared/ai/conversationContextRules.ts`（命名区分）

**影响**：高。如果直接搬 v2 文件，TypeScript 会有命名冲突 + 路径解析歧义；mobile 现有 `conversationRules.ts` 的调用方都得改。

### 偏差 #3：Phase 2.5 "adapters.ts 扩展 API 路径"——职责混淆

**计划声称**：
> 2.5 `composables/ai/adapters.ts` 扩展：对接 AI 网关 API 路径（替代或补充现有直连方式）

**仓库事实**：
- `adapters.ts`（68 行）目前是**模式适配层**（answerAdapter / trainingAdapter），负责不同 AI 模式的**消息转换**（入参结构、消息字段映射、welcomeMessage 构造）
- API 路径对接应该由 `api/ai/aiGateway.ts`（Phase 2.1 新增）承担
- 这两个职责**不应该混淆**

**修复建议**：
- Phase 2.5 改为：`adapters.ts` 扩展——补充训练模式的消息转换（如果还没覆盖）+ 接入 aiGateway 的发送函数
- 不再写"对接 AI 网关 API 路径"——那是 aiGateway.ts 的事

**影响**：中等。避免后续代码组织混乱。

## 五、新发现的潜在问题（深入核对发现）

### 5.1 mobile 端 `composables/ai/` 位置问题

**事实**：
- plan §1.2 把 `pages/smart-training/composables/ai/` 标为"位置待评估"
- plan §2.3 又写"扩展（在 smart-training 内或提升为全局）"
- Phase 0.5 决策项："评估 pages/smart-training/ 内 vs 全局 composables 的位置决策"

**问题**：位置决策的**判定标准**没有写。Phase 0.5 决策者会卡。

**建议补**：在 Phase 0.5 增加判定准则：
- 如果 AI 功能只服务于 smart-training → 留在 `pages/smart-training/composables/ai/`
- 如果还要服务于其他模块（如 im/inbox） → 提升到 `src/composables/ai/`
- 当前仓库 AI 调用方有 9 个文件（见 grep 结果）— 列出它们就能判定

### 5.2 后端 SSE 事件与 v3 sseStream.ts 的协议鸿沟

**事实**：
- v3 `sseStream.ts`（271 行）：注释明确"v3 简化 SSE 解析（只处理标准 data: / [DONE] 格式）"
- 后端 AgentChatChunkVo：13 种事件，**每种事件 type 字段区分**（不是 SSE 标准 `data: [DONE]`）

**问题**：v3 `sseStream.ts` 是否真的支持 13 种事件路由？plan §1.1 直接说"换 token 获取即可直接复用"——**这是错的**。

**实际需要做**：
1. 读 v3 sseStream.ts 全文，确认它是否真的只能处理 `data: / [DONE]`
2. 如果是，Phase 1.1 就要扩展为支持 `type` 字段路由（13 种事件对应 13 个回调）
3. 或者：直接重写为 mobile 专用 `shared/ai/aiGatewaySse.ts`

**建议补**：Phase 1.1 步骤拆为：
- 1.1a：从 v3 复制 `sseStream.ts` 基础
- 1.1b：**评估并扩展 type 字段路由**（如果 v3 不支持）
- 1.1c：替换 token 获取为 mobile 方式

### 5.3 Phase 3 与 Phase 5 的依赖关系反了

**计划声称**（§4 依赖图）：
```
Phase 3 (核心聊天 + ReAct 节点)
  └→ Phase 5 (训练模式)
```

**问题**：Phase 5.6 `TrainingAssistantView.vue` 升级集成开场白 + 评分 + 训练状态管理，但开场白（Phase 5.1）和评分（Phase 5.2）属于**流式响应处理**，应该依赖 Phase 3 的 SSE 处理能力。

**实际依赖**：
- Phase 5.1 `openingRemarkUseCase.ts` → 依赖 Phase 1（sseStream）
- Phase 5.2 `endTrainingUseCase.ts` → 依赖 Phase 1（sseStream）
- Phase 5.6 集成 → 依赖 Phase 3（ReAct 节点）

**当前计划的 Phase 5.1/5.2 依赖 Phase 1**，**Phase 5.6 依赖 Phase 3**——这块逻辑是对的，但 §4 图示画成了"Phase 3 → Phase 5（线性）"，容易让人误以为"Phase 5 必须等 Phase 3 全做完"。

**建议补**：§4 依赖图拆开：
```
Phase 1 (共享逻辑层)
  ├→ Phase 2 (API + 会话引擎)
  │    ├→ Phase 3 (核心聊天 + ReAct 节点)
  │    │    └→ Phase 5.6 (TrainingAssistantView 集成)
  │    └→ Phase 4 (语音 + 文件) ← 可并行
  └→ Phase 5.1-5.2 (开场白 + 评分 useCase) ← 可与 Phase 3 并行
```

### 5.4 后端 `interrupt` / `progress` 事件缺前端实现

**计划声称**（§1.3 SSE 事件协议）：
> `progress`：进度信息（M1.1 预留）— 当前忽略
> `interrupt`：人机交互暂停（M1.1 预留）— 当前忽略

**问题**：M1.1 是后端 AgentChatChunkVo 注释中的里程碑标识。**如果 mobile 端在 M1.1 之前上线，前端不需要管这两个事件**；但如果 mobile 上线时后端已经推到 M1.1，前端必须实现。

**决策点缺失**：Phase 0 必须确认**mobile 端发布日期 vs 后端 M1.1 发布时间**。

**建议补**：Phase 0 增加 0.6：与后端确认 M1.1 时间线，决定 progress/interrupt 事件是否实现。

### 5.5 13 种 SSE 事件的 TypeScript 类型定义来源

**计划声称**（Phase 2.3）：
> 补充 13 种 SSE chunk 类型定义（参照后端 `AgentChatChunkVo`）

**问题**：mobile 端如何**自动同步**后端类型变更？

**方案**：
- 选项 A：手写 TS 类型（容易漂移）
- 选项 B：后端导出 OpenAPI schema → 前端生成（理想但需基础设施）
- 选项 C：从后端 Java DTO 自动生成 TS 类型（feign/openapi-generator）

**建议补**：Phase 2.3 注明类型生成方案。短期手写 + 注释标注"以 AgentChatChunkVo 为准"，中期推动 OpenAPI 生成。
