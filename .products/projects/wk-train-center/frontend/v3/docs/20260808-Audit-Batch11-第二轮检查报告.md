#### 3.1.2 问题 2：handleSave async/await 与 callback 混用（潜在 BUG）

**V3 旧行为**（line 166-189）：

```ts
async function handleSave() {
  if (!postFormRef.value) return
  await postFormRef.value.validate(async (valid) => {  // ❌ Element Plus validate() 返回 Promise<boolean>,不需要 callback
    if (!valid) return
    // ...
    try {
      // API 调用
    } catch (err) { ... }
  })
}
```

**问题分析**：

Element Plus 的 `formRef.validate()` 方法签名：

```ts
// 1. callback 形式（V2 风格）
validate(callback: (isValid: boolean, invalidFields?: ValidateErrorField[]) => void): Promise<void>
// 2. promise 形式（V3 推荐）
validate(): Promise<boolean>
```

**V3 旧行为同时传 callback 且 await 会有副作用**：

1. `validate(callback)` 在校验失败时**不会 reject**，而是 resolve undefined 之后调用 callback
2. callback 中的 `if (!valid) return` 仅阻止 callback 后续逻辑，不影响外层 await（因为外层 await 永远 resolve）
3. callback 中的 try/catch 异常不会冒泡到外层 handleSave
4. 表单字段校验失败的真正错误提示由 Element Plus 自动显示（红字 + 红框），但用户不知道后续保存逻辑

### 3.3 🔴 NodeCardAll.vue — 失去 userDeadline 节点时间窗判定

**V2 行为**（line 113-145）：

```js
props: {
  planId: String,
  node: Object,
  userDeadline: String  // ← 接收个人截止时间
},
computed: {
  timeState() {
    const now = Date.now()
    const start = this.node.startTime ? new Date(this.node.startTime).getTime() : null
    const nodeEnd = this.node.endTime ? new Date(this.node.endTime).getTime() : null
    const personal = this.userDeadline ? new Date(this.userDeadline).getTime() : null
    // 延期只延长不缩短:取节点结束时间与个人截止时间中较晚者作为上限
    let end = nodeEnd
    if (personal !== null && (end === null || personal > end)) {
      end = personal
    }
    if (start !== null && now < start) return 'before'
    if (end !== null && now > end) return 'after'
    return 'normal'
  }
}
```

**V3 旧行为**：

```ts

  planId: string
  node: PlanNode
  // ❌ 无 userDeadline prop
}>()

const timeState = computed<'before' | 'after' | 'normal'>(() => {

  const start = props.node.startTime ? new Date(props.node.startTime).getTime() : null
```

**业务影响**：

- 学员被延期到 2026-12-31（userDeadline = 2026-12-31）
- 节点 endTime 是 2026-08-01（已过期）
- V2：timeState = 'normal'（取 nodeEnd 2026-08-01 和 personal 2026-12-31 中较晚者 2026-12-31），节点显示"在时间窗内"，按钮"去学习"可点击

**V3 修复**：


### 3.4 🔴 CourseDetail.vue — faceApi.check 函数不存在（严重运行时 BUG）

**问题**：

V3 CourseDetail.vue 第 219 行调用：

```ts
import * as faceApi from '@/api/admin/course/face'
// ...
const res = await faceApi.check({ courseId: courseId.value, fileId: currentFile.value.fileId })
```

但 `src/api/admin/course/face.ts` 第 30-58 行导出的函数为：

```ts
export function saveCapture(data: CaptureData): Promise<ApiResponse<void>> { ... }
export function validateFace(data: { ... }): Promise<ApiResponse<boolean>> { ... }  // ← 真实存在的函数
export function facePaging(data: ...) { ... }
export function capturePaging(data: ...) { ... }
```

**`face.ts` 中没有 `check` 函数**！

V2 CourseDetail.vue 第 399 行调用的是 `validateFace(...)`：

```js

  courseId: this.courseId,
  fileId: this.currentFile.fileId
}).then((res) => {
  this.faceVisible = !res.data
  this.faceChecked = res.data
})
```

V3 重构时把 `validateFace` 误写为 `check`，导致运行时 `TypeError: faceApi.check is not a function`。

**为什么 build 没失败**：

- Vite 生产构建对 `import * as faceApi from '...'` 模块的属性访问不做静态检查（不会因为模块没有 `check` 导出而报错）
- `npm run typecheck`（vue-tsc）也未报错，因为 `import *` 会推导为 namespace 类型，TypeScript 不强制存在性检查
- Vite 在第一次 build 时**曾有警告**：`"check" is not exported by "src/api/admin/course/face.ts"` ——这个警告正是 BUG 的信号！但 Vite 只警告不报错，导致开发者未注意到

**业务影响**：

1. 学员切换课件文件触发 `changeFile` → 调用 `doCheckFace`
2. `doCheckFace` 调用 `faceApi.check(...)` → 抛 `TypeError: faceApi.check is not a function`
3. 异常被 try/catch 捕获，提示"人脸识别失败"
4. **`faceChecked.value` 永远是 false**
5. **课程学习 Tab 永远不会显示**——所有开启了人脸识别的课程完全无法进入

**严重度**：🔴 阻断级（开启了人脸识别的课程对所有学员完全不可用）

**V3 修复**：

```diff
   try {
-    const res = await faceApi.check({ courseId: courseId.value, fileId: currentFile.value.fileId })
+    const res = await faceApi.validateFace({ courseId: courseId.value, fileId: currentFile.value.fileId })
     if (res.data) {
       faceChecked.value = true
     }
```

修复后 Vite build 警告 `"check" is not exported` 消失，确认 BUG 修复。

**重要性**：🔴 阻断级——必修

## 6. 审计方法论沉淀

### 6.1 发现手段

1. **运行 `scripts/diff-v2-v3.cjs`**：对所有 V3 已存在但 V2/V3 行数差 > 50 的文件做完整 diff（不仅看头尾，要看全文）
2. **关注 Vite build 警告**：即使是 warning（如 `"check" is not exported`），也可能代表真实 BUG——不要忽略
3. **V2 中的 dead code 不能作为"安全删除"的理由**：必须先确认 V2 真的未使用，再判断 V3 删除是否合理（本次审计发现 V2 keyListener 是 dead code，但仍然选择保守记录）
4. **关注计算属性 / props**：组件间通过 props 传递的业务标志（如 `userDeadline`），容易在现代化重构时被遗忘
5. **关注 `import * as xxx` 模式**：namespace import 不会做命名检查，函数名拼写错误不会在 typecheck/build 中报错

### 6.2 建议

1. **将 faceApi 模块改为命名导入**：`import { validateFace } from '...'`，避免 `import * as` 的宽松检查
2. **CI 中开启严格 typecheck**：在 `tsconfig.check.json` 中启用 `noImplicitAny` + `noUncheckedIndexedAccess`，强制 namespace import 检查
3. **Vite build 警告升级为错误**：在 `vite.config.ts` 中将 warning 视为 error 处理
4. **Audit 周期化**：建议每月一次"业务丢失扫描"，特别关注带 `:user-deadline` / `:user-id` 等业务标志 prop 的组件
5. **Batch 8 报告修订**：按 §1.3 修订建议更新"keyListener 迁移"描述
