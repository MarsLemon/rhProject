## 📋 协作规则

### **文件命名规范**

所有审计报告必须按以下格式命名:

```
N-<类型>-M-Y-D-H-M-T.txt
```

| 字段 | 说明 | 示例 |
|------|------|------|
| N | 会话轮次序号 (数字) | 1, 2, 3... |
| <类型> | plan (实行方) / review (审核方) | plan, review |
| M | 交互轮次序号 (数字) | 1, 2, 3... |
| Y | 月份 (2 位) | 08 |
| D | 日期 (2 位) | 26 |
| H | 小时 (2 位, 24 小时制) | 10 |
| M | 分钟 (2 位) | 23 |
| T | 主题名称 (简写, 下划线分隔) | api_call_audit, vuex_pinia_check |

**完整示例:**
```
1-plan-1-8-26-10-23-api_call_audit.txt     # 第 1 轮对话 - 实行方计划
1-review-1-8-26-10-23-api_call_audit.txt   # 第 1 轮对话 - 审核方审查
1-plan-2-8-26-11-45-vuex_pinia_check.txt   # 第 2 轮对话 - 实行方执行
1-review-2-8-26-11-45-vuex_pinia_check.txt # 第 2 轮对话 - 审核方审查
```

### **工作流程**

#### **阶段 1: 首轮对话**

1. **实行方 (Plan)** → 生成 `1-plan-1-XXX.txt`
   - 明确任务目标
   - 列出具体步骤
   - 给出预期结果

2. **审核方 (Review)** → 生成 `1-review-1-XXX.txt`
   - 审核 Plan 的完整性
   - 指出遗漏或错误
   - 提出改进建议

3. **如有歧义** → 双方各自收集证据 → 进入阶段 2

#### **阶段 2+: 后续轮次**

1. **实行方** → 生成 `N-plan-M-XXX.txt`
   - 基于上一轮的 Review 调整
   - 继续执行未完成任务

2. **审核方** → 生成 `N-review-M-XXX.txt`
   - 审核新 Plan 的执行情况
   - 标记已解决的问题
   - 提出新发现的问题

### **内容要求**

#### **Plan 文档 (实行方)**

每个主题文档必须包含:

```markdown
# [主题名称] 实行计划

## 任务背景
[为什么要做这件事]

## 目标
[期望达成的结果]

## 具体步骤
1. 第一步
2. 第二步
...

## 预期结果
[完成后的状态]

## 所需资源
[需要的文件、数据、工具等]

## 风险与应对
[可能的问题和解决方案]
```

#### **Review 文档 (审核方)**

每个主题文档必须包含:

```markdown
# [主题名称] 审核报告

## 审核范围
[检查了哪些方面]

## 结论
✅ 通过 / ❌ 不通过 / ⚠️ 需整改

## 详细审查
### ✅ 做得好的地方
- 优点 1
- 优点 2

### ❌ 存在的问题
1. 问题 1 + 证据
2. 问题 2 + 证据

### ⚠️ 建议改进
1. 建议 1
2. 建议 2

## 证据清单
[相关代码片段、日志截图、数据等]

## 后续行动
[下一步要做什么]
```

---

### **冲突处理原则**

当 Plan 和 Review 出现矛盾时:

1. **立即停止** → 不要强行推进
2. **双方收集证据** → 提供代码、日志、测试结果等
3. **记录在案** → 在各自的文档中注明争议点
4. **第三方裁决** → 等待主人决策或进一步讨论
5. **记录决策** → 最终决定写入新的文档

## 🔄 会话管理

### **何时开始新会话？**

- 主人明确要求"换个话题"
- 当前话题已完成 (达到 Phase Complete)
- 出现了重大方向性变化
- 超过 3 小时无进展

### **何时继续同一会话？**

- 当前话题还有未完成的任务
- 正在进行迭代优化
- 需要延续上次的上下文
