## 1. 整体评价

**方向正确，修复的"幻觉源"是真问题**。现状 [AgentReActExecutorImpl.java:965-969](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk/traincenter/ai/application/react/AgentReActExecutorImpl.java#L965-L969) `buildFileSummaryCacheKey` 仅依赖 `fileIds` 列表，`Integer.toHexString(combined.hashCode())` 还会因整数 hash 冲突导致不同文件集共用同一摘要（Java 32-bit hash 在 1000+ 条数据时碰撞概率约 4.3e-8，但多租户多会话下会累积）。换问题复用旧摘要确实是 [2026-07-23-ai-architecture-mind-gaps-review P0-3](../../mobile/1.5/design/mobile1.2/2026-07-23-ai-architecture-mind-gaps-review(claude).md) 的延伸问题。

**但计划缺 4 件关键配套**，单独跑这一份改动会引入新的不一致与幻觉源：

1. **P0-3 截断未联动**（P1-1）—— 计划没把"逐文件后 N 份摘要拼接"的总字数上限、history 压缩、KB 截断三件套一起做。**单文件摘要 30KB × 5 文件 = 150KB 注入 system prompt，下游主模型 context window 直接爆**。
2. **未校验 `dashScopeFileId` 必传字段存在性**（P1-2）—— 计划 §1 假设 `dashScopeFileId != null` 的项才收集；现状 [FileItem.java](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk/traincenter/ai/controller/model/FileItem.java) 已支持 `url-only` 旧格式（无 dashScopeFileId 时 name 也为 null）。需要明确"无 dashScopeFileId 的文件**整条跳过 vs 走 URL 兜底**"，否则新逻辑会把"没上传到 DashScope 的纯 URL 文件"当成"无 fileId 静默成功 → 实际未读"。
3. **强制 `query` 字段为 required 是行为变更**（P1-3）—— 计划 §5 把 `query` 列入 `required`，意味着历史训练数据 / 已落库 prompt 调用本工具的代码（如果有）会触发主模型参数校验失败。
4. **前端阶段展示假设多文件会"自然分散为多个节点"未经前端代码验证**（P1-4）—— 计划 §6 凭印象"前端 ThoughtsSection 现有 fileRead 分支会为新文件新建节点"，但 [v2 ThoughtsSection.vue:485-509](../../wk-train-center-ui/src/views/web/ai/components/AiAssistant/components/ThoughtsSection.vue#L485-L509) 实际是"如果上一阶段 type=fileRead 且未 finished 就覆盖同一个 stage 的 thought/summary"，**不新建节点**。多文件需要不同 key 才会被识别为新阶段。

## 3. Important (P1 — SHOULD FIX，开工前必须补)

### P1-1. 计划未联动 P0-3 截断三件套，下游 context window 爆雷风险高

**类别**：跨模块 / 上下文管理

**证据**：

- 计划 §2 把所有文件逐个调 qwen-long 提取摘要，再"拼成带分隔的合并文本返回主模型"。如 5 个文件 × 30KB 摘要 ≈ **150KB 注入 system prompt**，加上 history（[2026-07-23-ai-architecture-mind-gaps-review(claude).md §P0-1](../../mobile/1.5/design/mobile1.2/2026-07-23-ai-architecture-mind-gaps-review(claude).md) 已警示"10 轮 O(N²) 增长"）轻松破 200KB。qwen-long 输出是文本摘要（非结构化），主模型 context window 会被压满触发"截断"或"丢消息"行为。
- [2026-07-22-ai-architecture-gaps-fix-progress(claude).md §三](../tasks/2026-07-22-ai-architecture-gaps-fix-progress(claude).md) P0-3a/b/c **本就在等待**：
  - P0-3a：`KnowledgeBaseSearchTool` KB 结果截断（`ai-agent.tools.kb-search.max-result-chars` 默认 20000）
  - P0-3b：`summarizeFilesWithQwenLong` 摘要截断
  - P0-3c：history 压缩 `compactHistory()`（已标"建议单独立项"）
- 计划全文未引用 P0-3b，**单做逐文件会放大 P0-3 风险**。

**修复**：

1. 计划 §2 末尾增加硬约束：
   ```java
   // 逐文件摘要累计超 60KB 触发截断（按 UTF-8 字符数估算,留 2/3 主模型窗口给 history + 用户问题）
   private static final int FILE_SUMMARY_TOTAL_BUDGET = 60_000;
   int totalChars = 0;
   for (FileSummary fs : perFileResults) {
       totalChars += fs.summary.length();
       if (totalChars > FILE_SUMMARY_TOTAL_BUDGET) {
           fs.summary = "[已截断] " + fs.summary.substring(0, FILE_SUMMARY_TOTAL_BUDGET - totalChars) + "…";
       }
   }
   ```
2. 计划 §4 缓存 key 拼"文件+问题"的同时，**写入元数据记 summaryLen**，命中时若 sumaryLen > 预算同样截断。
3. 计划文件头部加交叉引用，明确"本计划与 P0-3 修复配套实施"，或明示"分两期、本期仅做提取语义，P0-3 截断另起计划"。

### P1-2. 未定义"无 dashScopeFileId 文件"的处理策略——隐式静默成功

**类别**：边界 / 异常处理

**证据**：

- 计划 §1：`AiRequestContext` 加 `FILE_NAMES`，§2：`遍历 fileIds，对每个文件单独处理`——前提是 `fileIds` 不为空。
- 现状 [AgentReActExecutorImpl.java:388-399](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk/traincenter/ai/application/react/AgentReActExecutorImpl.java#L388-L399) `executeReadUploadedFilesTool` 已有"无 fileIds → ToolResult.fail"，**新逻辑也会继承**。
- 但 [FileItem.java](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk/traincenter/ai/controller/model/FileItem.java) 同时支持：
  - 旧格式：`fileList: ["url1"]` → `FileItem{url:"url1", dashScopeFileId:null, name:null}`（L27 注释明示）
  - 对象格式：`{url:"url1", dashScopeFileId:null, name:"文件.pdf"}`（L28 注释明示）
- 计划 §1 隐含"只收集 `dashScopeFileId != null` 的项"。这意味着 **URL-only 旧格式 + name 字段有值的文件，新版本会被静默跳过**：
  - 用户期望：基于 URL 走 DashScope 上传或 OSS 临时凭证读取
  - 现状：直接 404，前端"已读取"显示"读取失败"或根本无节点
- 计划未明确"无 fileId 文件"的兜底路径（直连 URL 读取 / 调百炼 file-search / 报错退出）

**修复**：

1. 计划 §2 增加分流：
   ```text
   遍历 fileList（不是 fileIds）：
     - 有 dashScopeFileId → 走 qwen-long fileid:// 路径
     - 无 dashScopeFileId + 有 url → 走百炼 file_search 路径（带 file_url）
     - 都没有 → emitFileReadingStage("失败：{name} 缺少读取凭据", detail="文件既无 dashScopeFileId 也无可用 URL")
   ```
2. 计划 §1 改语义：`FILE_NAMES` 应该是 `List<FileItem>` 全量，**不是 `Map<fileId, name>`**——避免丢掉无 fileId 的项。
3. 工具描述 §5 同步加："若文件未上传到 DashScope，工具会尝试走 URL 直读；都不行返回失败"。

### P1-3. `query` 强制 required 是**行为变更**，需明确兼容性

**类别**：API 契约 / 兼容性

**证据**：

- 计划 §5："并将其列入 `required`（强制主模型给出检索目标；执行侧仍对空值兜底用 userPrompt）"
- 现状 [ReadUploadedFilesTool.java:40-52](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk/traincenter/ai/application/tool/ReadUploadedFilesTool.java#L40-L52) `query` 在 schema 里是 optional
- 兼容性影响：
  1. 主模型（qwen3.6-plus / glm-5.2）历史上调用过这个工具不传 query 的话，新 schema 会让 function-calling 直接拒收 → 工具调用失败 → 主模型改走"基于 history 推断"路径，**用户体验明显变化**（之前是"自动总结全文"，现在变"不调用工具"）
  2. OpenAI 兼容协议下，required 字段缺失会触发 400 而非"静默用 userPrompt 兜底"
- 计划说"执行侧仍对空值兜底"——但**工具描述里被引导传 query 反而会让主模型传空字符串 `""`**（OpenAI function-calling 不会把缺字段视为 null），导致 `tc.arguments.has("query") && !isNull()` 误判。

**修复**：

1. 计划 §5 明确"两步走"：
   - 工具 schema 仍把 `query` 列为 optional
   - 工具描述里"强烈建议传入"（已经写了）
   - 执行侧 `query` 为空字符串或缺字段时，仍用 `request.userPrompt()` 兜底（计划已正确）
2. 计划增加"主模型 prompt 行为验证"步骤：复现"主模型不传 query"的旧调用路径，确认新描述不会**完全禁止**主模型省略 query。
3. 写明"如果发现新描述导致主模型强制不省略 query 而传空字符串" 的回退策略。

### P1-4. 计划 §6 假设"前端会为多文件自动分散节点"——与现状不符

**类别**：跨端契约 / 前端假设

**证据**：

- 计划 §6："前端 `ThoughtsSection` 现有 fileRead 分支：上一个 fileRead 已 finished → 为下一文件新建节点，因此多文件会呈现多个「文件读取 {name}」节点"
- 现状 [v2 ThoughtsSection.vue:485-509](../../wk-train-center-ui/src/views/web/ai/components/AiAssistant/components/ThoughtsSection.vue#L485-L509) 实际是：
  ```js
  if (lastStage && lastStage.type === 'fileRead' && !lastStage.finished) {
    // 同一 stage 替换 thought + detailText
    this.$set(lastStage, 'detailText', obj.summary)
  } else {
    // 新建 fileRead stage
    const key = `fileRead_${this.stages.length}_${Date.now()}`
    ...
  }
  ```
  - **只有"上一 stage 未 finished"才会更新** —— 如果新逻辑里**第 N 份文件摘要"立即 finished"**（因为是同步 qwen-long callSync），下一份到达时会走"新建 stage"分支。✅ 看起来 OK
  - **但**计划 §2 写"先 emit '正在读取 {name}…' placeholder，qwen-long 完成后 emit '已读取 {name}（摘要 N 字）'"。**这两个 stage 的 type 都是 fileRead**，第二个到达时第一个**已 finished**（因为 placeholder 一次性 emit），所以会新建 ✅
- 真正的问题：**`key` 用 `length + Date.now()`**（v2 L503），多文件几乎同时 emit 时 key 冲突概率不低
- v3 [ThoughtsSection.vue:215-388](../../wk-train-center-ui-v3/src/views/web/ai/components/AiAssistant/components/ThoughtsSection.vue#L215-L388) 看似结构不同（按 stage 数组渲染），但同样没看到"按文件区分"的去重逻辑

**修复**：

1. 计划 §6 明确前端契约：后端 emit 的"已读取 {name}"的 `thought` 文本里**必须带文件名**（已写"已读取 {name}（摘要 N 字）"——✅），且 `item.thought` 中嵌入的文件名要让前端能 parse。
2. 计划 §6 增加前端验证步骤（不要"无需改前端"一笔带过）：
   - 用 3 个不同文件名（合同.xlsx、说明.pdf、规格.docx）发一条问题，确认 ThoughtsSection 渲染出 3 个独立 fileRead 节点。
   - 确认 v2 / v3 两个前端项目都通过。
3. 建议后端 `emitFileReadingStage` 给 item 加一个**稳定 id 字段**（如 `file_read_{fileId}`），前端按 id 去重，避免多文件同时到达 key 冲突。

## 4. Improvement (P2 — 改进)

### P2-1. `buildFileExtractPrompt` 缺乏「失败可见性」硬约束

**类别**：反幻觉 / 可观测性

**证据**：

- 计划 §3 列出 4 条反幻觉硬约束（只输出存在 / 不输出无关 / "未找到" 标注 / 优先原文），**未提及"模型主动报告失败时如何处理"**。
- 现状 [BailianChatCaller.callSync](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk\traincenter\ai\application\react\BailianChatCaller.java#L378) 失败时抛 `BailianHttpException`（401/403/429/500），由 §P1-1 提到的 try-catch 兜底 → emit "文件读取失败：…" 节点。
- 计划 §2："任一文件失败：该文件段落写明「【读取失败】{name}: {原因}」"——只处理 HTTP 异常，**没处理 qwen-long 返回内容不可信**（如返回内容明显不是该文件内容、或者仅说"无法访问"）。

**修复**：

1. 计划 §2 末尾增加"输出可信度校验"：
   - qwen-long 返回内容若 > 80% 是模板话术（如"很抱歉，我无法…"），按失败处理
   - 失败时该文件段写"【读取失败】{name}: 模型无法提取有效内容"
2. 计划 §4 缓存 key 加"模型版本"维度：qwen-long 模型升级时旧摘要失效（避免模型能力变化 → 摘要风格变化 → 旧缓存误导主模型）

### P2-2. 阶段展示文案无边界防御

**类别**：UX / 边界

**证据**：

- 计划 §6："label 带文件名"——若 `name` 为 null（旧格式 URL-only 文件）则 label 是空字符串
- 计划 §3 反幻觉硬约束可被 qwen-long 反驳（如返回 "I am sorry…"）——失败提示文案需统一

**修复**：

1. emit `thought` 文本中 `{name}` 为空时回退到 `fileid://{id}` 截断 16 字符作标识
2. 失败/未找到的提示文案统一前缀「【未找到】」「【读取失败】」便于前端 grep

### P2-3. Test Plan 缺"老数据兼容"验证

**类别**：测试 / 验证

**证据**：

- 计划 Test Plan 仅 4 条浏览器复验（xlsx 表头 / 换问题 / 找不到 / 多文件节点），**未验证缓存迁移**：
  - 旧缓存 key 形如 `ai:file:summary:{int hash}`，新 key 形如 `ai:file:summary:{hex hash(fileId|query)}`，**完全不兼容**
  - 部署后老缓存自然过期 1 小时 TTL，但**首小时线上会有"老缓存格式不命中 → 全部重读 → 短暂 QPS 飙升"** 风险
- 未验证 [2026-07-22-ai-architecture-gaps-fix-progress(claude).md) §三 P0-3b 摘要截断](../tasks/2026-07-22-ai-architecture-gaps-fix-progress(claude).md) 是否在同窗口落地

**修复**：

1. Test Plan 增加："部署后观察 1 小时 redis 缓存命中率；预期首小时 < 50% 是正常（旧 key 过期），1 小时后 > 90%"
2. Test Plan 增加："新 key 格式 + 老 key 共存 1 小时不冲突"（实际必然不冲突，hash 空间不同）
3. 增加"并发场景"：同一 fileId 同 query 两次并发请求，确认不重复读 qwen-long（Redis setnx 或 Redis 锁）

### P2-4. 未提及"工具描述"对主模型行为的影响边界

**类别**：LLM 信任边界

**证据**：

- 计划 §5："补充'调用时请在 query 中传入用户当前的具体问题/信息需求，工具会据此在文件中定向查找'"
- 计划说"工具会据此在文件中定向查找"——但实际是"工具会据此**指导 qwen-long 摘要**"。两者有微妙差异：前者暗示工具自己定向查（实际 qwen-long 是 AI 摘要），后者才准确。
- 主模型对"工具能力"的理解偏差会导致"主模型相信工具会精确抽取单元格" → 当 qwen-long 摘要中漏掉某行数据时主模型**不会二次确认**。

**修复**：

1. 工具描述改为："工具会用 qwen-long **生成围绕该问题的文件摘要**（AI 摘要，不保证完全准确，重要数据建议追问）"
2. 计划 §3 末尾加"摘要可信度元数据"——把"截断位置 / 模型版本 / 文件 hash"附在每条摘要前，提示主模型"这段是摘要不是原文"。

### P2-5. 假设 `qwen-long` 支持的类型与文档脱节风险

**类别**：外部依赖

**证据**：

- 计划 §3 Assumptions：`qwen-long（DashScope file-extract）支持 xlsx/pptx/docx/pdf/txt 的正文抽取`
- 官方文档（[file-search](https://help.aliyun.com/zh/model-studio/file-search)）未对 `qwen-long` 单独列出"按文件类型分别侧重"的支持矩阵——计划 §3 的"xlsx 列表头 / pptx 按幻灯片"是**主模型 qwen-long 自然语言理解的偏好**，不是"qwen-long 内部不同模型分支"。**「按类型侧重」实际是 prompt 工程，不是 qwen-long 的能力差异**。
- 这意味着 §3 的反幻觉约束必须**用 prompt 强约束**，而不是依赖 qwen-long 内部逻辑

**修复**：

1. 计划 §3 Assumptions 改："qwen-long 通过自然语言理解能从各类文件中提取信息；类型侧重通过 prompt 引导，非模型内置能力"
2. 计划 §3 反幻觉约束增加"明确的禁止性 prompt"，如"绝对不要输出未在文件中出现的数字/字段名"
