# 文件读取问题驱动重构

## 目标

当前 `summarizeFilesWithQwenLong` 对所有文件一律「总结核心内容」，且缓存只按 fileId（换问题复用旧摘要）→ 幻觉严重。改造为：**逐文件 + 按类型侧重（Excel 看表头/PDF 看章节）+ 以用户问题为中心定向提取 + 强反幻觉约束 + 按「文件+问题」缓存**。两条 ReAct 路径（Chat Completions / Responses）共用同一函数，改一处两条都生效。

## 1. 透传文件名/类型到读取路径

现状：`AiRequestContext` 只存 `FILE_IDS`，读取时拿不到类型。

- `AiRequestContext.java`：新增 `ThreadLocal<java.util.Map<String,String>> FILE_NAMES`（fileId → 文件名），加 `setFileNames/getFileNames`，并在 `clear()` 里 **与 KB_CHOOSE/KB_LIST/FILE_IDS 一起 remove**（评审跨模块项：防 ThreadLocal 泄漏，必须补这一行）。
- `AgentReActExecutorImpl.execute()`（约 L72，`setFileIds` 旁）：新增 `AiRequestContext.setFileNames(buildFileIdNameMap(request.fileList()))`。新增私有方法 `buildFileIdNameMap(List<FileItem>)`：遍历 fileList，仅收集 `dashScopeFileId != null` 的项 → `fileId → name`。
- **范围界定（评审 P1-2）**：本次只处理"已上传到 DashScope（有 dashScopeFileId）"的文件，与现状 `extractFileIds` 一致；纯 URL 文档（旧格式、无 dashScopeFileId）本就不被 `read_uploaded_files` 读取，**保持不变**，不在本次引入 URL 直读 / file_search 兜底（属独立特性，另行立项）。

## 2. 逐文件 + 类型感知 + 问题驱动提取（核心）

重写 `AgentReActExecutorImpl.summarizeFilesWithQwenLong(fileIds, queryHint, systemPrompt, requestId, sink)`（L908-960）：

- 遍历 `fileIds`，对每个文件单独处理：
  1. 从 `AiRequestContext.getFileNames()` 取文件名 → 解析扩展名 `ext`（小写；名缺失则 ext="" 走通用，**label 回退用 `fileid://`+id 前 16 字符**，评审 P2-2）。
  2. per-file 缓存查询（见第 4 节 key）。
  3. 未命中：`emitFileReadingStage` 发"正在读取 {name}…"占位（**附稳定 id `file_read_{fileId}`**，评审 P1-4）；构造 qwen-long 请求（`model=qwen-long`, `stream=false`），messages = `[system(systemPrompt 可选), system("fileid://"+fileId), user(buildFileExtractPrompt(ext, queryHint))]`；`BailianChatCaller.callSync`。
  4. **失败归因（评审 P2-1 + P1-5）**：每个文件的 qwen-long 调用用**独立 try-catch 包裹**，按来源分档，**绝不让异常冒泡到 ReAct 全局 catch**（否则整个对话报 AI_INTERNAL，违背"单文件失败不影响其它"承诺）：
     - summary 为空/纯空白 → "【读取失败】{name}: 文件预读返回空内容"
     - 命中拒答模式（以"抱歉/无法/对不起/I'm sorry/cannot"开头且无实质内容）→ "【读取失败】{name}: 模型拒答（前 50 字: …）"
     - `BailianHttpException` → "【读取失败】{name}: 网络/服务异常 {errorCode}"
     - 其它 `RuntimeException` → "【读取失败】{name}: 模型调用异常 {msg}"
  5. 写缓存（**仅成功时写**）；`emitFileReadingStage` 发"已读取 {name}（摘要 N 字）" + summary 作为 detail（复用上一轮已加的 `detail` 参数）。
- 将每个文件结果拼成带分隔的合并文本返回主模型：
  ```
  【文件:合同.xlsx】
  <该文件的定向提取>

  【文件:说明.pdf】
  <该文件的定向提取>
  ```
- 上述任一失败档位：把对应"【读取失败】…"写入该文件段落，**继续处理下一文件、不中断整体**（失败隔离由第 4 步的独立 try-catch 保证）。
- **总量截断（评审 P1-1 = P0-3b）**：合并文本累计上限 `FILE_SUMMARY_TOTAL_BUDGET`（默认 40000 字符，给主模型窗口留 history + 用户问题余量），超限对后续文件段落截断并标"[已截断]"。这是 P0-3b（文件摘要截断）本身；**P0-3a（KB 结果截断）/ P0-3c（history 压缩）为独立项，不在本计划范围**。

新增私有方法 `buildFileExtractPrompt(String ext, String queryHint)`，按类型拼提示词（见第 3 节）。

## 3. 类型感知 + 反幻觉提示词（buildFileExtractPrompt）

统一开头注入用户问题，统一结尾加反幻觉硬约束；中间按类型给侧重：

- 通用头：`【用户问题】{queryHint}\n请仅围绕上述问题，从本文件中提取相关信息。`
- xlsx/xls：先列出每个工作表的表头(列名)及含义；再挑出与问题相关的行，保留原始单元格值（禁止虚构数字），用 markdown 表格呈现。
- pdf/docx/doc：先定位与问题相关的章节/小标题；摘录相关段落原文并标注出处章节；无关章节略过。
- pptx：按幻灯片列出与问题相关的页标题 + 要点原文。
- txt：摘录与问题相关的原文段落。
- 其他/未知 ext：通用「围绕问题摘录相关原文」。
- 统一反幻觉结尾（所有类型）：
  1. 只输出文件中确实存在的内容，禁止推断/补全/编造；
  2. 只提取与问题相关内容，无关不输出；
  3. 找不到相关内容必须写"【未找到】文件中没有与该问题相关的内容"，不得用通用知识填充；
  4. 优先原文摘录关键句/数据，而非改写；
  5. **明确禁止（评审 P2-5）：绝对不要输出未在文件中出现的数字、字段名、专有名词。**

`queryHint` 沿用现有回退逻辑（`read_uploaded_files` 的 `query` 为空时用 `request.userPrompt()`），保证始终问题驱动。

## 4. 缓存修复（按 文件+问题）

- `buildFileSummaryCacheKey` 改为按单文件：`key = "ai:file:summary:" + hex(hash(fileId + "|" + normalize(queryHint)))`。**不拼 model 维度（评审 P2-6）**：model 现写死 `qwen-long`，拼进去只是常量、无收益且是维护陷阱；改为在 qwen-long 升级/替换时由发版钩子显式 `redisService.delByPattern("ai:file:summary:*")` 清缓存（更可控）。
- `normalize(queryHint)`：trim + 折叠空白（避免同问题不同空格重复读）。
- TTL 保持 1 小时。效果：同文件同问题命中缓存；换问题重新定向读取，消除"换问题复用旧摘要"的幻觉源。
- **缓存迁移说明（评审 P2-3）**：新 key 格式（含 fileId|query）与旧 key（`int hash`）不同，部署后老缓存 1 小时内自然过期、hash 空间不重叠不冲突；首小时命中率偏低属正常。并发去重（同 fileId+query 同时到达重复读 qwen-long）不在本次范围。

## 5. 强化工具描述（评审 P1-3：query 保持 optional）

`ReadUploadedFilesTool.java`：

- `getParametersSchema()`：`query` **仍为 optional**（★ 不列入 `required`——强制 required 会让主模型历史"不传 query"的调用触发 function-calling 400 / 行为突变，且模型可能改传空字符串反而绕过兜底）。description 改为"用户当前关于文件的具体问题（用于在文件中定向提取相关内容，强烈建议传入）"。
- `getDescription()`：补充"工具会用 qwen-long **生成围绕该问题的文件摘要（AI 摘要，不保证逐字完全准确，关键数据建议追问核对）**"（评审 P2-4：措辞准确，避免主模型误信"精确抽取单元格"而不二次确认）。
- 执行侧：`query` 为空字符串 / 缺字段时仍用 `request.userPrompt()` 兜底（已正确，保持）。

## 6. 阶段展示（逐文件，仅 v2 前端）

- 每个文件各 emit 一对 `emitFileReadingStage`（占位→完成），`thought` 文本带文件名，并**附稳定 id `file_read_{fileId}`**（评审 P1-4：降低前端 `key=length+Date.now()` 的冲突风险；前端可选按 id 去重）。
- v2 前端（`wk-train-center-ui`，:4212 现网在跑）现有 fileRead 分支：占位一次性 emit 即 finished，下一文件到达走"新建节点"分支 → 多文件呈现多个「文件读取 {name}」节点，各自可展开 `detailText`。经评审确认逻辑成立，**无需改 v2 前端**。
- **v3（`wk-train-center-ui-v3`）本次不做**（主人 2026-07-24 拍板）：不验证、不改动。

## Assumptions

- qwen-long 通过自然语言理解从各类文件提取信息；**"按类型侧重"由 prompt 引导实现，非 qwen-long 内置的类型分支能力**（评审 P2-5）。
- 逐文件多次调用带来的额外延迟 / token 已被接受（换取精度与低幻觉）。
- **纯 URL（无 dashScopeFileId）文档不在本次读取范围**，行为同现状；不引入 URL 直读 / file_search 兜底。
- 仅重构文件读取的"提取"环节，不改 ReAct 主循环、工具注册机制、两条路径分流；不改 v2 前端渲染逻辑、**不动 v3**。
- **关联 P0-3**：本计划含 P0-3b（文件摘要总量截断）；P0-3a（KB 结果截断）与 P0-3c（history 压缩）为独立项，不在本范围。
