## 2. v2 复审新发现的缺陷

### P1-5（新）— callSync 失败类型不可区分，"拒答" 与 "网络异常" 会混淆

**类别**：异常处理 / 失败归因

**证据**：

- 计划 §2 第 4 条：「结果可信度校验：summary 为空/纯空白，或整体命中明显拒答模式（以"抱歉/无法/对不起/I'm sorry/cannot"开头且无实质内容）→ 按失败处理」
- 现状 [BailianChatCaller.java:411-439](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk\traincenter\ai\application\react\BailianChatCaller.java#L411-L439) `callSync`：
  - HTTP 4xx/5xx → `throw new IOException("百炼 API HTTP " + ...)` (L416)
  - HTTP 200 + 业务 `error` 字段 → `throw new IOException("百炼 API 错误 code=" + ...)` (L424)
  - 上述都会被 `catch (IOException e)` 捕获 → `throw new RuntimeException("文件预读失败: " + e.getMessage(), e)` (L438)
- 但**还有一个失败路径**：HTTP 200 + `choices[0].message.content` 为空字符串（qwen-long 真拒答但 HTTP 成功）—— 当前 L428 / L435 直接 `return ""`，**不抛异常**
- 计划 §2 第 4 条"summary 为空/纯空白"匹配的就是这条路径——但**仅基于返回字符串内容判断**，无法区分：
  - 路径 A：qwen-long 真正拒答（"抱歉…"）→ 应归类"读取失败:模型拒答"
  - 路径 B：网络慢导致超时但 HTTP 返回 200 + 空 body（边界情况）→ 应归类"读取失败:网络异常"
  - 路径 C：文件本身是空文件 → 应归类"【未找到】"

**风险**：

- 误归因：路径 A/B/C 都被混为"读取失败"，运营查日志时无法定位"到底是模型不配合还是网络抖"
- 静默成功：callSync 失败但 RuntimeException 没被 §2 try-catch 吞掉时，**整个 ReAct 循环会冒泡到 L91-109 catch 块**，前端收到 `AI_INTERNAL` 错误（见 [BailianHttpException / 5 类错误码 2026-07-22-ai-architecture-gaps-fix-progress P0-2](../../tasks/mobile1.2/2026-07-22-ai-architecture-gaps-fix-progress(claude).md)），**用户看到的不是"该文件读取失败"而是"整个对话崩了"**
- 与"任一文件失败不影响其它文件"的承诺（计划 §2 第 5 条）矛盾

**修复**：

1. 计划 §2 第 4 条细化三档失败原因（按 source 区分）：
   ```java
   if (summary == null || summary.isBlank()) {
       return new FileReadResult("empty", "【读取失败】{name}: 文件预读返回空内容");
   }
   if (isRefusalPattern(summary)) {
       return new FileReadResult("refusal", "【读取失败】{name}: qwen-long 拒答 (内容前 50 字符: " + preview + ")");
   }
   // 兜底：网络/IO 异常 — callSync 会 throw，§2 try-catch 捕获
   ```
2. 计划 §2 异常捕获增加"按异常类型分流"：
   ```java
   } catch (BailianHttpException e) {
       return new FileReadResult("network", "【读取失败】{name}: 网络异常 " + e.getErrorCode());
   } catch (RuntimeException e) {
       return new FileReadResult("model", "【读取失败】{name}: 模型调用异常 " + e.getMessage());
   }
   ```
3. 这样前端 / 日志都能看到"该文件独立失败"而非"全局崩了"。

**严重性**：P1（影响线上日志可读性 + 边界路径行为）—— 不阻塞开工，但**第一次发现 P0-3a/P0-3c 联调时很可能踩这个雷**。

### P2-6（新）— 缓存 key 加 model 维度的副作用：硬编码 "qwen-long"

**类别**：可维护性

**证据**：

- 计划 §4："加 model 维度（评审 P2-1）：模型升级时旧摘要自动失效"
- 现状 [AgentReActExecutorImpl.java:937-942](../../wk-train-center-service/wk-modules/wk-module-ai/src/main/java/com/wk\traincenter\ai\application\react\AgentReActExecutorImpl.java#L937-L942) 写死 `model("qwen-long")`
- 缓存 key 用 `model` 拼，如果未来支持"按用户配置选不同 model 读文件"（如 gpt-4o-mini / claude-3-haiku），**每个 model 一份缓存，缓存命中率被稀释**

**修复**：

1. 计划 §4 改为 `key = "...:" + hex(hash(fileId + "|" + normalize(queryHint)))`（去掉 model 维度）
2. 在 `BailianChatCaller` 升级 / 替换 qwen-long 时，**显式调 `redisService.delByPattern("ai:file:summary:*")`** 清缓存（一次发版钩子里加），比"按 model 维度自然过期"更可控
3. 或者保留 model 维度但在注释里写明"未来加 model 时记得同步升级清缓存脚本"

**严重性**：P2（设计权衡）—— 不阻塞开工，**记入开工后技术债**。

### P2-7（新）— "fileid://+id 前 16 字符"作 label 在某些场景下不可读

**类别**：UX 边界

**证据**：

- 计划 §2 第 1 条：「label 回退用 `fileid://`+id 前 16 字符」（评审 P2-2）
- DashScope file-id 格式示例：`file-2024-01-15-abc123def456` —— 前 16 字符是 `file-2024-01-15` 之类，**对用户无意义**

**修复**：

1. 前端 `ThoughtsSection` 接收稳定 id `file_read_{fileId}` 后，**自己根据 fileId 反查文件名**（如果后端传来的 item 同时带 fileId 字段）
2. 或者在主流程入口用 fileId 末 8 字符（哈希风格）作 fallback label
3. 计划 §6 末建议加一条："前端可选：fileId → 短哈希 label 映射"

**严重性**：P2（边角 UX）—— 不阻塞开工。
