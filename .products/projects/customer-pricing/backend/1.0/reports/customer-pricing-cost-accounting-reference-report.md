## 1. 背景

### 1.1 领导意图

客户定价当前公式是固定的(标准工时 × 职级费率 × 影响系数)。领导要求参考成本大表的计价逻辑(公司销售内部用的成熟体系,支持 6 种定价法 + 多级审批)。

**关键问题**:**外部客户询价**场景,如何借鉴**内部销售定价**的设计?

### 1.2 报告范围

- **做**:分析客户定价与成本大表的差异,识别可借鉴的设计思想,给出借鉴方案
- **不做**:不重写现有公式;不复制内部 4 级审批(场景不匹配)

---

## 2. 现状盘点:客户定价当前计价

### 2.1 业务一句话

客户(船东/船管)在嵌入页面自助完成"选设备 → 填需求 → 选方案 → 看预算 → 提交询价",系统实时算出预算,生成询价单邮件推送给销售跟进。

### 2.2 当前公式

```
行金额 = Σ(职级费率 × 人数) × 单件标准工时 × 数量
合计保底价 = Σ(每项人员配置综合费率 × 最低计费工时)
最终报价 = Max(合计保底价, 明细合计) × 影响系数
影响系数 = Max(紧急系数, 地点系数, 时间系数)
```

### 2.3 已有好设计

- **两层结构**:目录定价(后台维护)+ 询价定价(客户上下文)— 已是好设计
- **快照冻结**:询价单提交时锁定 16 个推导要素
- **客户侧口径**:客户只看最终报价,明细只进销售邮件

### 2.4 当前痛点

| #   | 痛点                | 业务影响                                   |
| --- | ------------------- | ------------------------------------------ |
| 1   | 定价公式写死        | 未来加新定价模式(批量优惠、客户分级)要大改 |
| 2   | 默认 USD,无汇率机制 | 国外客户用本币询价要销售人工换算           |
| 3   | 销售确认无系统约束  | 销售自由定价无 audit trail,合规风险        |

## 3. 参考对象:成本大表计价逻辑要点

### 3.1 核心组成

| 维度         | 成本大表怎么做                                        |
| ------------ | ----------------------------------------------------- |
| **定价方法** | 6 种(成本加成/市场导向/边际成本/效用/自定义/其他费用) |
| **方法切换** | 同一项目可选不同方法,新增方法不破坏现有               |
| **审批机制** | 4 级审批 + 售价区间硬约束                             |
| **币种**     | 多币种 + 汇率快照(锁定时点)                           |
| **关联**     | 报价 ↔ 成本项 多对多(可追溯)                          |

### 3.2 6 种定价法分类

**主报价方法(4 种)**:

- 成本加成 — 简单项目,成本 + 加成
- 市场导向 — 看竞品行情
- 边际成本 — 大批量设备(船套单位)
- 效用 — 按客户使用价值

**附加项方法(2 种)**:

- 自定义 — 兜底
- 其他费用/佣金 — 挂账用

### 3.3 关键设计思想(可借鉴)

| 思想               | 价值                       |
| ------------------ | -------------------------- |
| **定价方法可插拔** | 加新方法不动现有数据       |
| **汇率提交时锁定** | 避免汇率波动反复改历史报价 |
| **多对多关联**     | 报价有依据,审计可回溯      |

## 5. 借鉴方案

### 5.1 借鉴 1:定价方法"可插拔" ⭐P0

#### 现状痛点

客户定价当前是单一公式,业务新增定价模式(批量优惠、VIP 客户价、紧急加价)需修改核心公式 — 改造成本高、回归测试重、未来扩展受限。

#### 改造方案

**核心思想**:把"定价方法"从写死公式升级为**可切换的多种方法**。

```
未来客户定价可支持的定价方法:

├─ 标准工时定价     ← 当前(保留)
├─ 批量折扣定价     ← 新增(预留)
├─ 客户分级定价     ← 新增(预留)
└─ 紧急加价定价     ← 新增(预留,业务方已有紧急系数)
```

**机制**:

- 每份询价单选择"用哪种定价方法"
- 不同方法需要销售填不同字段(类似成本大表的初步/修正定价)
- 各方法独立计算、独立测试

#### 业务价值

| 价值     | 说明                                   |
| -------- | -------------------------------------- |
| 未来扩展 | 加新方法不动现有数据                   |
| 回归安全 | 各方法独立,改一个不影响其他            |
| 业务灵活 | 批量采购、VIP 客户、紧急订单可独立定价 |

#### 工作量

| 阶段                             | 工作量      |
| -------------------------------- | ----------- |
| 数据模型(询价单加"定价方法"字段) | 2 天        |
| 各定价方法实现 + 公式迁移        | 3 天        |
| 工厂模式(根据方法选算法)         | 2 天        |
| 前端适配(询价表单 + 详情页)      | 3 天        |
| 测试 + 回归                      | 2 天        |
| **合计**                         | **约 2 周** |

#### 风险

| 风险               | 缓解                          |
| ------------------ | ----------------------------- |
| 现有询价单数据迁移 | 旧数据默认"标准工时定价",不动 |
| 前端改造范围大     | 分两期:先服务端,前端渐进迁移  |
| 业务方需求边界模糊 | §7 决策点 1                   |

---

### 5.2 借鉴 2:跨币种 + 汇率快照 ⭐P1

#### 现状痛点

客户定价默认 USD,无汇率机制。国外客户若想用本币(欧元/人民币)询价,需销售人工换算 — 增加沟通成本,且汇率波动时报价可能与最终成交偏差大。

#### 改造方案

**核心思想**:询价提交时按汇率快照锁定,支持多币种展示与计算。

```
客户询价时可选币种:
├─ 美元(USD,默认)
├─ 人民币(CNY)
└─ 欧元(EUR)
```

**机制**:

- 询价时选币种
- 提交瞬间按当时汇率**快照锁定**(类似成本大表的 `foundationService.saveProjectBaseData`)
- 销售邮件双币种展示(原币种 + USD)
- 询价详情页显示汇率快照信息(汇率值、汇率日期)

#### 业务价值

| 价值     | 说明                            |
| -------- | ------------------------------- |
| 客户体验 | 国外客户可用本币询价,无沟通成本 |
| 报价稳定 | 汇率快照锁定,避免汇率波动反复改 |
| 追溯     | 询价单可见汇率来源与日期        |

#### 工作量

| 阶段                          | 工作量      |
| ----------------------------- | ----------- |
| 数据模型扩展(币种 + 汇率快照) | 1 天        |
| 汇率服务(取汇率 + 锁定机制)   | 2 天        |
| 前端币种选择 + 双币种展示     | 2 天        |
| 邮件模板改造                  | 1 天        |
| 测试                          | 1 天        |
| **合计**                      | **约 1 周** |

#### 风险

| 风险                     | 缓解                        |
| ------------------------ | --------------------------- |
| 汇率数据源选择           | 优先内部维护,后续接外部 API |
| 多币种下影响系数是否一致 | 系数不变,只影响货币转换     |
| 历史数据兼容             | 旧询价单币种=USD,汇率=1.0   |

## 6. 不建议借鉴(为什么不做)

| #   | 项                                | 不建议原因                                                     |
| --- | --------------------------------- | -------------------------------------------------------------- |
| 1   | **4 级内部审批**                  | 客户询价是参考,最终报价由销售人工确认,系统内置审批反而拖慢流程 |
| 2   | **16 项成本类型**                 | 客户侧不需要看成本构成(D17 已决策),复制过来无价值              |
| 3   | **多部门并行填成本**              | 客户侧无"多部门协同定价"场景,客户是单一角色                    |
| 4   | **报价↔成本多对多**               | 客户询价是黑盒,无需追溯到内部成本明细                          |
| 5   | **基础数据 + 4 级审批的售价区间** | 同 #1,客户侧不需要                                             |

**核心判断**:**借鉴"设计思想"(可切换、快照),不复制"业务流程"(多级审批、多部门协同)**。

## 8. 实施路径(开发看)

### 8.1 阶段化(串行)

```
P0: 可插拔定价方法(2 周)
├─ W1: 数据模型 + 各定价方法 + 公式迁移
├─ W2: 工厂机制 + 前端适配 + 测试

P1: 跨币种 + 汇率快照(1 周,P0 完成后启动)
├─ W3: 数据扩展 + 汇率服务 + 快照机制
└─ W4: 前端币种 + 邮件模板 + 测试

合计:4 周
```

### 8.2 关键里程碑

| 时间  | 里程碑                                     |
| ----- | ------------------------------------------ |
| W1 末 | 可插拔定价方法可用,现有询价单不受影响      |
| W2 末 | 前端询价表单支持定价方法选择(默认标准工时) |
| W3 末 | 汇率服务上线,可手动配置汇率                |
| W4 末 | 跨币种询价端到端跑通,邮件双币种展示        |

### 8.3 数据迁移

| 迁移项             | 策略                  |
| ------------------ | --------------------- |
| 现有询价单定价方法 | 默认"标准工时定价"    |
| 现有询价单币种     | 默认 USD              |
| 现有询价单汇率     | 默认 1.0              |

## 附录 B:术语表

| 术语           | 解释                                                   |
| -------------- | ------------------------------------------------------ |
| 定价方法可插拔 | 同一系统支持多种定价方式,可切换、可扩展                |
| 快照           | 在某一时点冻结数据,后续修改不影响历史值                |
| 影响系数       | 乘数,根据外部条件(紧急/地点/时间)调整最终报价          |
| 询价单         | 客户提交的价格咨询请求,含客户信息 + 设备 + 方案 + 快照 |
| 询价定价       | 客户上下文驱动的实时价格计算                           |
| 目录定价       | 后台维护的标准价格体系                                 |
| 审计追溯       | 任何报价都有依据,可回溯到定价时的快照数据              |
