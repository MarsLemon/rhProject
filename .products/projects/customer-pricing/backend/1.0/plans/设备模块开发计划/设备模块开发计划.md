## 1. 背景与定位

设备（equipment）是**设备目录的第三个维护对象**（FR-07 维护顺序：① 厂家 → ② 设备分类树 → **③ 设备** → ④ 型号），是型号（model）与维保类型挂载（equipment_maintenance_type）的父级。

- **R-01（硬性规则）**：设备分类树仅用于导航。设备本身**不参与定价**，模块内不得出现价格/工时/费率字段；设备是型号、维保类型、服务项等子表的**挂载点**（parent_id）。
- **数据模型定位**（§3.3 ER）：`equipment_category ||--o{ equipment : "包含"` —— 1 个分类下挂多个设备。demo 当前把"分类叶子"当作设备用（`deviceLeaves()`），本期后端按 ER 设计独立建表，前端后续对接时融合（见 §6.3）。
- **依赖**：设备分类 ✅（code/parent_id）+ 厂家 ✅（型号多对多关联，本期不涉及）。后续依赖方：型号（依赖设备 + 厂家）、设备-维保类型挂载（依赖设备 + 维保类型）。
- **里程碑**：M1（目录+工时定价），设备目录 6 表完成第 3 张。

## 3. 业务规则基线

> 编号 BR-EQ-xx，源自 R-01 + §6.2.3 表 + demo 行为提炼，写代码注释/测试名时引用。

| 编号     | 规则                                                                                                                                                                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BR-EQ-01 | 设备 code 由系统按层级自动生成：`父分类 code + "." + 同父下现存最大序号 + 1`（3 位宽），禁止手填；同父序号删除后不复用（防外部引用漂移，与设备分类/厂家口径一致）                                                                                                                |
| BR-EQ-02 | 父分类必须存在、未删除、未停用（status=1）；停用父分类时新增设备被拒，提示"父分类已停用，请先启用"                                                                                                                                                                               |
| BR-EQ-03 | 中文名必填（≤100 字）；英文名选填（≤200 字）；中英文均参与列表关键词过滤（不区分大小写）                                                                                                                                                                                         |
| BR-EQ-04 | `status`：1=启用 0=停用。停用后前台 by-category 不可见、nav-tree 该节点隐藏；后台 /list 仍可见（前端置灰）；可重新启用                                                                                                                                                           |
| BR-EQ-05 | 删除采用逻辑删除（state=3）；本期仅校验存在性 + 未删除，"被型号关联不可删"校验随型号模块补账（领域服务注释标注依赖点）                                                                                                                                                           |
| BR-EQ-06 | 跨模块补账——本模块完成后，**解除**设备分类模块的"挂载设备不可删/设备叶子不可加子级"校验的前置锁：分类模块删除校验需检查"存在未删除设备 → 拒绝"（已在设备分类计划 §12 风险表标注，本期在分类模块补一行即可，不在设备模块动作）                                                    |
| BR-EQ-07 | 设备不参与任何定价解析：模块内零定价字段/计价引用；与产品分离（R-01）                                                                                                                                                                                                            |
| BR-EQ-08 | 所有写操作记录操作人快照（platform operator 快照列）+ `log.info` 关键节点日志                                                                                                                                                                                                    |
| BR-EQ-09 | 父分类停用时**前台可见性传播**：by-category 与 nav-tree 接口均按"前台可见性约定"对该子孙做隐藏/返空集处理，与设备分类模块"父停用 → 子孙前台隐藏"语义一致（联动设备分类 R-01，运维需先启用父分类才能让子孙前台可见）；后台 `/list` 不受此约束（仍返回停用父分类下设备，前端置灰） |
| BR-EQ-10 | **同 category_id 下中文名精确查重**（对齐 manufacturer BR-MFR-03）：同一分类下不允许重名，跨分类允许重名（不同分类下"舵机-1" vs "传感器-1" 无歧义）；应用层预校验 + uk_category_name(category_id, name) 唯一约束兜底                                                             |

## 4. 数据模型设计

### 4.1 建表 SQL（对齐设计文档 §6.2.3 + 工程表惯例）

> 惯例同 `wk_equipment_category` / `wk_manufacturer`：`wk_` 前缀、`state` 逻辑删除位、`create_time/create_operator/update_time/update_operator` 平台快照列替代设计文档的 `created_at/updated_at`；业务字段（category_id/code/name/name_en/status）原样保留。

```sql
-- 设备（分类叶子下的具体可维保设备；不参与定价，R-01）
CREATE TABLE IF NOT EXISTS `wk_equipment`
(
    `id`              BIGINT                                                        NOT NULL AUTO_INCREMENT COMMENT '主键id',
    `category_id`     BIGINT                                                        NOT NULL COMMENT '所属分类id（FK→wk_equipment_category.id）',
    `code`            VARCHAR(50) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci  NOT NULL COMMENT '设备编码，系统按 父分类code.3位序号 生成，全局唯一（BR-EQ01）',
    `name`            VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci NOT NULL COMMENT '设备中文名',
    `name_en`         VARCHAR(200) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci NULL     DEFAULT NULL COMMENT '设备英文名，中英双语搜索用',
    `status`          TINYINT                                                       NOT NULL DEFAULT 1 COMMENT '业务状态：1启用 0停用，停用后前台不可见（BR-EQ04）',
    `state`           TINYINT                                                       NOT NULL DEFAULT 1 COMMENT '数据状态：1.启用 2.冻结 3.删除',
    `create_time`     DATETIME                                                      NULL     DEFAULT NULL COMMENT '创建时间',
    `create_operator` JSON                                                          NULL     DEFAULT NULL COMMENT '创建人快照',
    `update_time`     DATETIME                                                      NULL     DEFAULT NULL COMMENT '更新时间',
    `update_operator` JSON                                                          NULL     DEFAULT NULL COMMENT '更新人快照',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_code` (`code`),
    UNIQUE KEY `uk_category_name` (`category_id`, `name`) COMMENT '同分类下中文名精确唯一（BR-EQ-10）',
    KEY `idx_category` (`category_id`)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_general_ci COMMENT ='设备（分类叶子下的具体可维保设备；不参与定价）';
```

### 4.2 设计要点

1. **平铺字典（无层级）**：仅一个 `category_id` 外键，无 parent_id；树由 category 决定，设备是叶子下挂载点。
2. **status 与 state 职责分离**：status = 业务启停（前台可见性）；state = 平台数据状态（逻辑删除）。
3. **外键约束不落库**：`category_id` 不加 FOREIGN KEY，保留纯应用层校验（与设备分类/厂家一致，工程惯例）。
4. **demo 融合策略**（§6.3）：demo `deviceLeaves()` 当前返回分类叶子；后端设备接口上线后，由前端聚合查询把设备按 category_id 挂入分类树（接口出参为嵌套树结构，天然支持合并）。

## 5. 领域模型与分层设计

### 5.1 领域模型（对齐 DDD §6.1）

- **EquipmentDomain（聚合根）**：id、categoryId、code、name、nameEn、status、state、平台快照字段（平铺风格对齐 EquipmentCategoryDomain / ManufacturerDomain）。
- **EquipmentDomainService**：code 生成（父 code + 3 位序号）、父分类存在性 + 启用态校验、name 校验、**父前缀防御校验（IN-EQ-07）**——纯 Java 纯函数，便于单测。
- **EquipmentTreeNodeDo（领域树节点）** vs **EquipmentTreeNodeBo（读视图）**：`Do` 仅含 `categoryId` + 该分类下设备叶子数组（**不含分类路径快照**——分类路径由应用层跨仓储拼接，避免领域层跨模块依赖设备分类），供 `AppQueryServiceImpl` 按 `category_id` 聚合后注入分类路径信息转 `Bo`；`Bo` 是按分类聚合后的读视图（含分类 `{id,code,name}` 摘要），Controller 不见 `Do`，最终 `Bo → Vo` 返回（保证 DDD Entity/Do 不外泄原则）

### 6.3 前台树与 demo 融合策略（衔接说明）

> **v1.1 修订（M1 拍板选项 C）**：设备模块不返“分类 + 设备”完整树，只返设备叶子数组；分类树仍由**设备分类模块**的 `/web/portal/equipment-category/nav-tree` 独立维护（该接口已交付并被前端消费，见设备分类接口对接文档 L369）。**前端组装**：marketing-ui 并行调两个 nav-tree，按 category_id 合并。与设备分类 plan §6.3 原有合并策略一致（“接口出参为嵌套树结构，天然支持合并，无需变更本模块契约”）。

- 后端 `nav-tree`：仅查 `wk_equipment` 启用状态记录，按 `category_id` 分组返嵌套结构，**不返分类节点本身**。
- demo 当前 `deviceLeaves()` 返回分类叶子 → 后续前端适配时调用设备分类 nav-tree + 设备 nav-tree 双源聚合；本期不动 demo 代码，单独维护。
