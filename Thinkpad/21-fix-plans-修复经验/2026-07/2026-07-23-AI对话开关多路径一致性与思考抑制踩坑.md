# AI 对话三开关多路径一致性与思考抑制踩坑

> **一句话**：AI 对话的「深度思考 / 联网搜索 / 知识检索」三开关，状态要穿透 `前端 UI → 发送参数 → 后端 Controller → 两条 ReAct 路径（Responses / Chat Completions）`。**任何抑制/终止/开关逻辑，只改一条路径 = 没改。** 抑制展示必须从后端源头做，别在前端按 `enableThoughts` 过滤（历史消息缺该字段会误伤）。

## 背景

`wk-train-center-ui`(Vue2) + `wk-train-center-service`(Java) 的 AI 问答。后端手写 ReAct 主循环，按 `apiMode.useResponsesApi`(默认 true) 分两条路径：
- **Responses API**（`runReactLoopResponses` + `BailianResponsesCaller`）：普通问答，用百炼**内置工具** file_search/web_search/web_extractor。
- **Chat Completions**（`runReactLoop` + `BailianChatCaller`）：**有文件上传（DashScope fileId）时强制走这条**（qwen-long 读文件），用自定义 function 工具。

一轮排查连带挖出 5 个坑，全部围绕「开关状态没贯穿到所有路径」。

## 坑 1：关闭深度思考 + 联网 + 知识库 → 后端流式「瞬间 done」

**现象**：三个全开正常；单独「关思考 + 开另外两个」→ 开流瞬间 done，不回答。

**根因**：Responses 路径，关思考 → `thinkingLevel='none'` → `reasoning.effort="none"`。百炼官方文档原话「**开启思考模式时，建议开启内置工具，以获得最佳模型效果**」——内置工具是**配合思考模式**设计的。`effort="none"` + 内置工具 → qwen3.6-plus 返回**退化空响应**（无正文、无工具调用）→ ReAct 首轮命中 `else { break; }` → 立即 done。

**修复**：有内置工具时，把 `effort` 下限从 `none` 抬到 `minimal`（`AgentReActExecutorImpl.runReactLoopResponses`）。既保证工具触发，又几乎不增推理 token；无工具的纯问答仍走 `none`。

## 坑 2：关思考仍显示「思考中」——且要覆盖两条路径

**要求**：关深度思考时，前端只看工具调用，不显示思考过程。

**根因**：坑 1 抬到 minimal 后模型仍可能吐少量 reasoning；且 **Chat Completions 路径（文件上传）的 `reasoning_content` 是无条件 emit 的**——即使 `enable_thinking=false`，qwen 有时仍吐思考。

**修复（两条路径都做，且必须从后端源头抑制）**：
- Responses：新增 `suppressReasoning` 标志（`userDisabledThinking` = effort 抬升前是否为 none），`reasoning_summary_text.delta` 仅累积 `fullThinking`、不 emit thoughts。
- Chat Completions：`reasoning_content` 的 emit 加门禁 `request.isEnableThinking()`。

**为什么不在前端过滤**：历史会话回看时 `mapOneRecord` 不还原 `enableThoughts`（库里没存）→ 前端按 `enableThoughts` 隐藏会**误伤**当初开着思考、有正常思考过程的老消息。后端抑制让「关思考」的消息压根不产生/不入库 reasoning，**新消息干净、历史一致、无回归**。

## 坑 3：只发「1」AI 却回答「11」——当前 user 消息被重复

**根因**：`chatSession.generateAiResponse` 先 push AI 占位消息，再 `slice(0, -1)` 建 history —— 只去掉 AI 占位，**当前 user 消息仍留在 history**；而 `buildStreamParams` 又把 `currentUserMsg`（同一条）push 一次 → `[..., user("1"), user("1")]` → 模型读成「11」。

**修复**：`slice(0, -1)` → `slice(0, -2)`，history 同时排除「AI 占位」和「当前 user」，当前 user 只由 `currentUserMsg` 带一次。**这是一直存在的潜在 bug**（每条消息都被重复发），长问题被模型脑补忽略，单字符才暴露。

## 坑 4：内置工具被当自定义 function 去执行 → `未注册的工具: web_search_call`

**根因**：`BailianResponsesCaller` 把内置工具项（`file_search_call`/`web_search_call` 等）也塞进 `toolCallsAccum` → 污染 `hasToolCalls` → 某轮无正文时 ReAct 拿 `web_search_call` 去 `toolRegistry` 执行 → 必然失败。内置工具**由百炼服务端执行**，结果随响应流直接回来，Java 端不该也无法再执行。

**修复**：`output_item.added` 内置工具分支去掉 `toolCallsAccum.put`（只保留 `emitToolCallStart` 供前端展示）；构建可执行 `toolCalls` 时用 `isBuiltinToolName` 兜底跳过。

## 坑 5：开关状态多层贯穿——单一事实源 + 双保险

- **深度思考死绑定**：`@toggle-thoughts="enableThoughts = !enableThoughts"` 会翻转 `enableThoughts` 却不同步 `thinkingLevel`。当前无人 emit（pill 走 `set-thinking-level`），但一旦启用 → 按钮显示关、后端因 `thinkingLevel` 优先仍开思考。**移除死绑定，`thinkingLevel` 为唯一源，`enableThoughts` 由 watcher 派生。**
- **占位口径不一致**：Chat Completions「思考中」占位用原始 `request.enableThinking()`，模型调用/抑制用 `effectiveEnableThinking`（含 thinkingLevel 优先级）→ 对齐为后者。
- **知识库关不掉双保险**：后端「空 kbList 兜底成 training」会掩盖「用户显式关闭」。前端关 KB 时发 `kbChoose='none'`，后端捕获 `kbExplicitlyNone` 参与 `enableKb` 判定，避免关了又被兜底开回来。（当前靠 `enableKbSearch=false` 也能关，双保险防未来回归。）

## 通用教训（红线）

- **多路径系统改一处 = 没改**：先确认生产实际走哪条路径（本例默认 Responses，但**文件上传强制 Chat Completions**），抑制/终止/开关逻辑必须覆盖全部路径 + 逐路径验证。
- **展示抑制从源头（后端）做**，不靠前端二次过滤——尤其当历史消息不持久化对应开关状态时，前端过滤必造历史回归。
- **一个语义一个事实源**：思考状态以 `thinkingLevel` 为准，`enableThoughts` 派生；双信号 + 死绑定是定时炸弹。
- **平台内置工具 ≠ 自定义工具**：内置工具服务端执行，绝不能进「待执行/回填」列表。
- **兜底默认值会掩盖显式意图**：`if (empty) default=X` 之前先捕获「用户显式关闭」信号。
