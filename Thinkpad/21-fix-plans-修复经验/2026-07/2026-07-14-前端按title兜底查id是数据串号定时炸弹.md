# 教训：前端按 title 兜底查 id = 数据串号定时炸弹

## 一句话

**后端 `save*` / `apiSave*` 接口必须 `resolve` 后返回真实 id（含 BaseIdRespDTO 或完整对象），前端禁止"按 title 兜底查 id"逻辑——只要业务允许重名，就是定时炸弹。**

## 反模式

```javascript
// ❌ 课程保存后,前端没拿到 id,按标题兜底
saveData(postForm).then((res) => {
  const savedId = res.data?.id
  if (!savedId && postForm.title) {
    fetchCoursePaging({ title: postForm.title }).then((paging) => {
      const firstMatch = paging.data.records[0]  // ← 假设标题唯一
      jumpToNextStep(firstMatch.id)
    })
  }
})
```

### 触发链

1. 管理员 A 创建课程"入职培训" → 拿到 id-X
2. 管理员 B 也创建课程"入职培训" → 后端也返 id-Y（正确）
3. 但前端兜底逻辑 `fetchCoursePaging({title})` → 拿到 records[0] = id-X（A 的）
4. 后续 B 的学习任务关联到 A 的课程 → **数据串号**

### 为什么"概率低"不是借口

- 重名发生概率确实不高，但**一旦发生 = 数据错乱且难追查**
- 多人同时操作、培训季批量创建时**概率显著上升**
- 串号后通常以"学员看到错误课程" / "管理员发现计划节点引用了奇怪 id" 暴露，**排查成本极高**

## 正模式：后端契约 + 前端直读

### 后端

```java
// Service.save(DTO) 必须返回新建/更新的 id
public String save(CourseDTO dto) {
    Course entity = new Course();
    BeanMapper.copy(dto, entity);
    entity.setId(IdWorker.getIdStr());   // 预生成,确保返回非空
    this.saveOrUpdate(entity);
    return entity.getId();
}

// Controller 包装为 ApiRest<BaseIdRespDTO>
@PostMapping("/save")
public ApiRest<BaseIdRespDTO> save(@RequestBody CourseDTO dto) {
    return success(new BaseIdRespDTO(courseService.save(dto)));
}
```

### 前端

```javascript
// ✅ 直接读后端返回的 id,无兜底
saveData(postForm).then((res) => {
  const savedId = res?.data?.id
  if (!savedId) {
    // 后端契约违反,显式报错而不是兜底
    this.$message.error('课程保存成功但未返回 id,请联系后端开发检查 save 接口')
    return
  }
  jumpToNextStep(savedId)
})
```

## 必须做的自检清单

- [ ] 业务是否允许重名（课程/考试/试卷/用户等）？
- [ ] 前端有 `if (!id) { fallbackLookupByTitle(...) }` 类逻辑吗？
- [ ] 后端 `save` / `apiSave` 接口返回类型是 `void` / `Boolean` / `R` / `BaseIdRespDTO`？
- [ ] 上线前抽查：保存一条数据，前端实际拿到的 id 是否与后端 DB 一致？

## 红线

**禁止**：前端在 save 后 id 为空时按 title/其他字段兜底查 id

**禁止**：后端 `save*` 接口返回 `void` 或 `Boolean`，必须返回 id（或 BaseIdRespDTO）

**强制**：save 接口契约变更必须前后端同步评审，禁止"前端自己兜底"
