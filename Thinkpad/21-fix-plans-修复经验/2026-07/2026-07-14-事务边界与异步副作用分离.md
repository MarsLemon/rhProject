# 教训：事务边界与异步副作用分离

## 一句话

**任何"清理 / 通知 / 广播 / 重建"型副作用，必须挂 `TransactionSynchronizationManager.registerSynchronization(afterCommit)`，禁止用 `CompletableFuture.runAsync` 直接脱离事务跑。**

## 触发场景

- `@Transactional` 方法内调用 `redis.del(...)` / `cache.clear()` / `mq.send(...)` / `webhook.post(...)`
- `runAsync` 或 `new Thread().start()` 包装业务清理逻辑
- 事务回滚后，副作用已发出（缓存已清 / 消息已发 / 第三方已调用）

## 反模式 vs 正模式

### ❌ 反模式

```java
@Transactional
public void saveRoleIds(String roleId, List<String> ids) {
    this.saveBatch(list);                       // 假设抛异常 → 回滚
    CompletableFuture.runAsync(() -> {
        redisService.del(getCacheKeys(roleId)); // 但异步已发出,缓存已清
    });
}
```

后果：DB 没变（回滚），但缓存已清 → 下次用户加载配置时拿到 stale 数据；若缓存重建逻辑有副作用，可能雪崩。

### ✅ 正模式（调用方注册钩子）

```java
@Transactional
public void saveRoleIds(String roleId, List<String> ids) {
    this.saveBatch(list);
    deferAfterCommit(() -> redisService.del(getCacheKeys(roleId)));
}

private void deferAfterCommit(Runnable task) {
    if (TransactionSynchronizationManager.isActualTransactionActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() { task.run(); }
        });
    } else {
        task.run();  // 无事务场景直接执行,不要挂空钩子
    }
}
```

### ✅ 正模式（impl 拆掉内层异步）

```java
// 之前:impl 内部 runAsync,调用方拿不到事务上下文
public void clearCache(String roleId) {
    CompletableFuture.runAsync(() -> { /* 清理 */ });
}

// 之后:impl 只剩同步逻辑,异步决策外移到调用方
public void clearCache(String roleId) {
    /* 同步清理,无内层异步 */
}
// 调用方用 deferAfterCommit 包装,事务环境由调用方掌控
```

## 决策树

```
"事务内要不要清缓存/发通知？"
  ├─ 是 → 注册 afterCommit 钩子(见上面模板)
  │       ├─ 有事务 → 钩子在 commit 后执行,回滚则不执行
  │       └─ 无事务 → 直接执行(用 isActualTransactionActive 兜底)
  └─ 否 → 用 @TransactionalEventListener(AFTER_COMMIT) 解耦
```

## 红线

**禁止**：`@Async + @Transactional` 同方法（Spring AOP 自调用失效，事务不生效，副作用同样裸跑）

**禁止**：`CompletableFuture.runAsync(() -> { redisService.del(...) })` 直接用在事务方法末尾
